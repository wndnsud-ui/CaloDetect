# CaloDetect 업무지시서 — 인식 실패 시 직접 등록 동선 개선

Nov 1, 2026 · @최혜영

AI가 음식을 인식하지 못해도 사용자가 항상 식단을 기록할 수 있도록, 인식 실패 시 대체 동선(검색 → 직접 입력)을 만든다. 이 작업은 150개 클래스 확대보다 먼저 완료한다.

## 1. 배경: 사용자 테스트 피드백

사용자 테스트에서 드러난 가장 큰 문제는 모델 정확도가 아니라 **AI가 실패했을 때 사용자가 갈 곳이 없다**는 점이었다.

| 사용자 피드백 | 원인 | 개선 방향 |
| --- | --- | --- |
| "순대국이 인식되지 않아요." | 인식 실패 시 다음 동선이 없어 기록이 끊김 | 실패·저신뢰 시 음식 검색으로 연결, 검색에도 없으면 직접 입력 |
| "분석하지 않고 사진만 등록할 수는 없나요?" | 기록이 AI 분석 결과에 묶여 있음 | 분석 없이 사진만 저장하고 영양 정보는 나중에 채움 |
| "식단의 모든 항목을 수정할 수 없어요." | AI 결과 중 일부 항목만 편집 가능 | 기록된 식단의 모든 항목을 수정 가능하게 변경 |

## 2. 목표와 우선순위

**목표: 어느 단계에서 분기하든 끝은 항상 '기록'이고, 막다른 화면이 없어야 한다.**

1. **1순위 — 인식 실패 → 직접 등록 동선 완성** (이번 업무지시서의 범위)
2. 2순위 — 인식 클래스 150개 확대 (1순위 완료 후 착수)

순서를 이렇게 잡은 이유: 클래스를 늘려도 모델이 모르는 음식은 항상 남는다. 대체 동선이 있어야 사용자가 이탈하지 않고, 직접 등록 데이터가 쌓이면 어떤 클래스부터 늘릴지 정하는 근거가 된다.

## 3. 개선 동선: AI Detection → Search → Manual Input → Record

AI가 실패하면 검색으로, 검색에도 없으면 사용자가 음식명·양만 입력하고 LLM이 칼로리와 탄·단·지를 추정해 기록한다. 저장된 값은 모두 나중에 수정할 수 있다.

## 4. 작업 항목

모든 작업은 혼자 진행한다. '순서' 칼럼대로 하나씩 끝낸다. 먼저 저장·수정을 열어 피드백 두 개(사진만 저장, 전체 수정)를 빠르게 해결하고, 그다음 실패 동선(검색 → LLM 추정)을 붙인다. 중간에 멈춰도 그때까지 만든 것은 바로 쓸 수 있다.

| ID | 영역 | 작업 | 상세 | 순서 |
| --- | --- | --- | --- | --- |
| D-1 | DB | 스키마 변경 | 5장 참고 (Supabase 마이그레이션) | 1 |
| D-2 | DB | 음식 DB 적재 | 식약처 식품영양성분 DB를 Supabase에 적재. 순대국 등 테스트 실패 음식 포함 여부 확인 | 2 |
| B-3 | 백엔드 | 식단 저장·수정 API | 사진만 있는 식단 저장 허용, 모든 필드 PATCH 허용, source·is\_edited 기록 | 3 |
| F-1 | 프론트 | "사진만 저장" 버튼 | 업로드 직후 \[AI 분석\] / \[사진만 저장\] 선택. 저장된 식단에 '영양 정보 입력 필요' 표시 | 4 |
| F-5 | 프론트 | 식단 전체 항목 수정 | 음식명, 양, 칼로리, 탄·단·지, 식사 시간, 사진 모두 수정. 항목 추가·삭제 가능 | 5 |
| B-1 | 백엔드 | 감지 API 응답 변경 | 항목별 confidence와 후보 Top-3 반환. 실패 시에도 200 + 빈 결과로 응답 | 6 |
| F-6 | 프론트 | AI 실패 화면 | 에러 대신 "음식을 찾지 못했어요" + 검색/직접 입력 버튼. 지방이 안내 문구 활용 | 7 |
| B-2 | 백엔드 | 음식 검색 API | 음식 DB 이름 검색(부분 일치), 결과에 1회 제공량당 영양 정보 포함 | 8 |
| F-3 | 프론트 | 음식 검색 화면 | 음식명 검색 → 결과 선택 → 양(g/인분) 선택. 결과 없으면 "직접 입력하기" 버튼 | 9 |
| B-4 | 백엔드 | LLM 영양 추정 API | 입력: 음식명 + 양. 출력: 칼로리·탄·단·지 JSON(숫자 검증 포함). Calo-T Coach와 같은 LLM 공급자 사용. 실패하면 값을 비워두고 사용자가 입력 | 10 |
| F-4 | 프론트 | 직접 입력 폼 + LLM 영양 추정 | 사용자는 음식명과 양만 입력. LLM이 칼로리·탄·단·지를 추정해 채우고 '추정값' 배지 표시. 사용자는 확인 후 기록하고 필요하면 수정 | 11 |
| F-2 | 프론트 | 저신뢰 결과 화면 | 신뢰도가 기준값 미만이면 후보 Top-3 + "다른 음식이에요" 버튼 노출 | 12 |

## 5. DB 변경 사항 (Supabase)

식사 단위에는 분석 상태를, 음식 항목 단위에는 "어디서 왔는지"와 "사용자가 고쳤는지"를 기록한다. 테이블·커럼명은 실제 스키마에 맞춰 조정한다.

```sql
-- 식사: 사진만 저장 허용
alter table meals
  add column analysis_status text default 'pending'
    check (analysis_status in ('pending','analyzed','skipped','failed'));

-- 음식 항목: 출처와 수정 여부 추적
alter table meal_items
  add column source text default 'ai'
    check (source in ('ai','search','manual')),
  add column ai_confidence real,
  add column is_edited boolean default false,
  add column is_llm_estimated boolean default false;
```

| 커럼 | 의미 | 활용 |
| --- | --- | --- |
| analysis\_status | pending 분석 전 · analyzed 완료 · skipped 사진만 저장 · failed 인식 실패 | '영양 정보 입력 필요' 표시, 실패율 집계 |
| source | ai · search · manual | manual로 많이 들어오는 음식 = 다음 클래스 후보 |
| ai\_confidence | AI 신뢰도 (0\~1) | 저신뢰 기준값 튜닝 |
| is\_edited | AI 결과를 사용자가 수정했는지 | 실제 오인식률 측정 |
| is\_llm\_estimated | 칼로리·탄·단·지가 LLM 추정값인지 | 화면에 '추정값' 배지 표시, 추정 후 수정률 측정 |

## 6. 완료 기준과 테스트 시나리오

아래 시나리오를 모바일과 PC에서 모두 통과하면 완료로 본다.

- [ ] 순대국 사진 업로드 → 인식 실패 → 검색에서 "순대국" 선택 → 기록 완료
- [ ] DB에 없는 음식 → 검색 결과 없음 → 음식명·양 입력 → LLM이 칼로리·탄·단·지 추정 → 확인 후 기록 완료
- [ ] 사진 업로드 → \[사진만 저장\] → 기록 완료, 나중에 영양 정보 추가 가능
- [ ] 저신뢰 결과 → Top-3 후보 중 선택 → 기록 완료
- [ ] 기록된 식단의 음식명, 양, 칼로리, 탄·단·지, 식사 시간, 사진을 모두 수정할 수 있음
- [ ] 어떤 동선에서도 에러 화면이나 막다른 화면에서 끝나지 않음
- [ ] 저장된 항목에 source(ai/search/manual)와 is\_edited가 올바르게 남음
- [ ] 테스트 참가자 재테스트에서 세 가지 피드백이 다시 나오지 않음

## 7. 범위 밖과 발표 반영

**이번 범위에서 제외:** 인식 클래스 150개 확대, 모델 재학습, Calo-T Coach 챗봇 작업.

**PPT에 추가할 슬라이드 1장 — "사용자 테스트 → 개선"**

- 발견한 문제: 인식 실패 시 기록 불가 · 사진만 저장 불가 · 일부 항목 수정 불가
- 인사이트: 정확도보다 실패했을 때의 대체 동선이 더 큰 문제였다
- 개선: AI Detection → Search → Manual Input → Record
- 결과: AI가 몰라도 사용자는 언제나 기록할 수 있다

이 슬라이드로 발표의 성격을 '기술 구현 프로젝트'에서 '사용자 문제를 발견하고 개선한 서비스 프로젝트'로 바꾼다.
