## ⚠️ Codex / Claude Code 구현 전 필수 경고

> **이 문서는 이미 구현된 리워드 Stage A/B/C 위에 얹는 증분 작업이다. 새로 만들지 말고 기존 구조를 확장할 것.** 착수 전 §0의 D1~D8 승인 기록과 §1의 C1~C12 확인을 먼저 끝내고 파일·줄 근거를 보고한다. 차단 조건은 임의 해결하지 말고 해당 작업만 멈춘다.

### 특히 주의할 점

- **기존 원장 유지:** 포인트는 `reward_point_lots → reward_point_spends → reward_point_allocations` 원장만 쓴다. 기획서의 `point_ledger`·`point_lots`·`point_allocations`·`bucket` 컬럼은 **새로 만들지 않는다**. 기존 테이블이 같은 역할을 한다(§3 대조표).
- **잠금 순서 유지:** `reward_accounts → reward_point_lots → reward_exchange_month_counters → reward_exchanges`. 코칭 이용권은 `reward_accounts → reward_point_lots → reward_coach_passes`. 잔액 부족 판정은 잠금 뒤에 한다.
- **기존 API 호환:** 기존 요청·응답 필드는 지우거나 의미를 바꾸지 않는다. 새 필드는 추가만 한다. 기존 상품 ID(`energy_bar` 등)는 바꾸지 않는다.
- **적립 수치 변경 금지:** 기획서 적립표(사진 3P, 3끼 5P 등)와 현재 `REWARD_*` 개발 기본값이 다르다. **이번 작업에서 적립 수치를 바꾸지 않는다.** 화면은 서버가 준 값만 표시한다(§3-2).
- **출처 제한 유지:** 온보딩·커뮤니티 계열 lot은 실물 교환과 코칭 이용권에 쓰지 않는다(`REWARD_EXCHANGE_EXCLUDED_SOURCES`).
- **첫 교환 보류·관리자 발급 유지:** 기획서의 "가상 쿠폰 자동 발급"은 적용하지 않는다. 현재의 `held` → 관리자 발급 흐름이 기준이다.
- **메뉴 구조는 2026-10-22 결정 기준:** 시안의 왼쪽 사이드바("음식 추가·목표 설정·…·코칭·리워드")와 리워드 상단 알약 메뉴는 적용하지 않는다(§7-0).
- **플래그 OFF 보호:** `REWARD_EXCHANGE_ENABLED=false`면 교환·쿠폰 API 404 유지. 새 코칭 이용권 API는 `REWARD_COACHING_ENABLED=false`(기본)면 404, 콜라보 기획전은 `REWARD_COLLAB_DEMO_ENABLED=false`(기본)면 노출하지 않는다.
- **표현 규칙:** 효능·기능 암시 문구 금지, 실존 브랜드 상품에 CaloDetect·CaloPoint 로고 금지, 시연용 수치는 "시연용" 표시(§8).
- **TBD 임의 확정 금지:** §9의 결정 대기 항목은 개발 기본값으로만 두고 운영값처럼 쓰지 않는다.

> **핵심 순서: `D1~D8 승인 기록 → C1~C12 확인 → 차단 판단 → M1 → M2 → M3 → M4 → M5`. 각 단계는 별도 PR.**

# 3. 기획서 v1.3 ↔ 현재 구현 대조

기획서는 리워드가 처음부터 없다고 가정하고 쓴 부분이 있다. 아래 표가 구현 기준이다.

## 3-1. 데이터·처리

| 기획서 v1.3 | 현재 구현 | 이번 작업 |
|---|---|---|
| `point_ledger` + `bucket`(deco\_only / general) | `reward_point_lots`(`source`, `restricted`) + `reward_point_spends` + `reward_point_allocations` | 새 테이블 없음. "꾸미기 전용" = 교환 제외 출처 lot |
| `point_lots` / `point_allocations` (v1.3 신설 제안) | 이미 있음 | 없음 |
| 잔액 = 원장 합 | `reward_accounts.balance_cache` + 원장에서 재계산 가능 | 없음 |
| `reward_exchanges.status` requested → issuing → issued → used / expired, cancelled·refunded | requested · held · issued · used · canceled · failed, 만료는 `coupon_expires_at`로 판정 | 없음. 화면 매핑만(§3-3) |
| `counts_monthly` 컬럼 | 월 횟수는 `ACTIVE` 상태만 세므로 취소·실패는 자동 제외 | 없음 |
| `idempotency_key`(교환) | 월 1회 제한 + 계정 잠금으로 중복 차단 | 교환은 추가하지 않음. 코칭 이용권만 `idem_key` |
| `user_goals` | `reward_accounts.goal_ref` (`item:<id>` / `product:<id>`) | 코칭 상품도 `product:<id>`로 목표 설정 허용 |
| `user_items` | `reward_user_items` + `reward_equipment` | 없음 |
| `reward_products`(category deco / health / coaching) | `reward_products`(category goods / ai / pro), 꾸미기는 `reward_items` | 카테고리 값 유지. 기획서 health = `goods`, coaching = `pro` |
| `coach_profiles` · `coach_contents` · `coach_passes` | 없음 | M4에서 `reward_coach_profiles` · `reward_coach_contents` · `reward_coach_passes`로 신설 |
| 가상 쿠폰 자동 발급 | 첫 교환 `held`, 관리자 번호 입력 발급, AES-GCM 암호화 | 유지 |

| 목표 칼로리 범위 | +3P | XP만 (`REWARD_BALANCE_XP`) |
| 커뮤니티 게시 | +2P, 교환 사용 가능 | +1P, 교환 제외 출처 |
| 7일 연속 | +20P | +10P |
| 가입 보너스 | 10P 꾸미기 전용 | 온보딩 3종 각 10P, 교환 제외 출처 |
| 실물 교환 | 가입 14일 · 월 1회 | 같음 + 첫 교환 보류 + 월 전체 상한 |
| 예상 일수 | 최근 7일 평균, 0이면 대체 문구 | 같음 (`REWARD_ETA_WINDOW_DAYS`, 제외 출처 반영) |

시안의 "포인트 모으는 법(+3P·+5P·+3P·+20P)"과 상품 상세의 "오늘 더 받을 수 있어요"는 **하드코딩하지 않고** 서버 설정값을 내려받아 표시한다. 필요하면 `GET /rewards/me`에 `earn_rules` 배열(라벨·포인트·조건)을 추가한다.

## 3-3. 쿠폰 상태 표시

| 시안·기획서 표기 | 서버 `state` | 서버 `status` |
|---|---|---|
| 발급 중 | `pending` | requested, held (held면 "운영자 확인 중" 보조 문구) |

## 6-2. 교환 신청 규칙 추가 (M1)

기존 `request_exchange` 흐름(지시서 v3 §6-11)에 아래를 넣는다. 순서와 잠금은 바꾸지 않는다.

1. 상품 조회 직후, 잠금 전에 입력 검사:
   - 옵션 있는 상품에 `option`이 없거나 목록에 없으면 422 `OPTION_REQUIRED`
   - `quantity < 1` 또는 `quantity > max_qty`면 422 `QTY_LIMIT_EXCEEDED`
   - `listed=false`여도 `active`·`available`이면 신청 가능. 콜라보이고 기획전 플래그 OFF면 404
2. 차감액 = `price × quantity`. 잔액 판정·차감·`Exchange.points` 모두 이 값을 쓴다.
3. `option_label`·`quantity`를 교환 행에 저장한다.
4. 월 1회·월 전체 상한은 수량과 상관없이 **교환 1건**으로 센다.
5. 취소·실패 환불은 기존 `refund`가 `points` 전체를 allocation 역순으로 되돌린다(변경 없음).
6. 로그는 지금처럼 상품 ID·포인트만 남긴다. 옵션·수량은 넣어도 되지만 쿠폰 번호·개인정보는 넣지 않는다.

## 6-3. 목표 리워드 (M2)

- `PUT /rewards/goal`은 `product:<id>`로 건강상품·콜라보·코칭 상품을 모두 받는다(코칭은 플래그 OFF면 400).
- 상품 목표의 기준 잔액은 지금처럼 **교환 가능 포인트**다(코칭도 같음).
- 목록·상세 응답의 `is_goal`로 현재 목표를 표시한다. 시안의 "이미 목표인데 [목표 리워드로 설정하기]가 보이는 상태"를 고친다.

3. 같은 `(user_id, idem_key)` 이용권이 있으면 그 결과를 200으로 그대로 돌려준다(연타 방지).
4. 같은 코치의 `in_use` 이용권이 있으면 409 `PASS_IN_USE` (D7).
5. 교환 가능 lot(제외 출처·`restricted` 제외)을 만료 빠른 순으로 `FOR UPDATE` 잠그고 합계 판정. 부족하면 409 `INSUFFICIENT_POINTS`.
6. `reward_point_spends(kind='coach_pass')` + allocation 생성, lot `remaining` 차감, 잔액 캐시 갱신.
7. `reward_coach_passes` 생성(`status='in_use'`, `sessions=7`).
8. 응답: 이용권 + 코치 `kakao_link`·`phone` + 남은 잔액.

- 가입 14일·월 1회·월 전체 상한은 코칭에 적용하지 않는다(기획서 정책). 첫 교환 보류도 적용하지 않는다.
- 사용자 취소 API는 없다. 코치 연락 불가 같은 예외는 관리자 수동 환불: `POST /admin/rewards/coach-passes/{id}/refund`(admin 권한 서버 검사, allocation 역순 환불, `status='refunded'`). 관리자 목록 `GET /admin/rewards/coach-passes`.
- 로그: 코치 ID·포인트만. 연락처 금지.

## 7-3. 상품 상세 (M1, 공통 템플릿 1개)

- **경로:** 리워드몰 › 건강상품 › {하위분류} › {상품명}
