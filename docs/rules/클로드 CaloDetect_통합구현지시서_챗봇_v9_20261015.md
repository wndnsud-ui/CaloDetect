## 0. 핵심 결과

**이 챗봇의 차별점은 "말하면 자동으로 데이터가 된다"는 것이다.** 비율 버튼, 조정 패널, 별도 저장 버튼은 기존 식단 직접 올리기와 다르지 않으므로 **만들지 않는다.**

흐름: 채팅에서 사진 촬영·선택 → 서버 분석(기존 YOLO) → 봇이 채팅 안에서 음식·kcal을 보여 주고 "얼마나 드셨어요?"라고 묻는다 → 사용자가 말한다("절반만 먹었어, 올려줘", "맞아 올려줘") → **서버가 식사로 자동 확정**해 DB에 저장 → 봇이 "기록했어요" 카드로 알린다. 우측 요약(오늘·최근 식사)과 히스토리·오늘·월간이 바로 갱신된다. 저장된 뒤의 양 수정도 말로 한다("아니, 4분의 1"). 대화·사진은 서버에 보존되어 재접속해도 복원된다.

## 2. 통합 시 확정한 결정 (에이전트가 바꾸지 않는다)

| 번호 | 쟁점 | 결정 | 근거 |
|---|---|---|---|
| R1 | 대화 이력 서버 저장 | **저장한다(A1).** 원문·응답·답장 칩 선택·상태·시각 보존. A0의 해석 API는 대화를 저장하지 않는다 | 사진 v4 요구가 섭취량 v4의 "저장 안 함"을 대체 |
| R2 | 멱등성 | `last_request_id` 단일 컬럼 **폐기**. `MutationRequest`(**(user_id, operation, request_id) unique** + payload hash + 결과 연결)로 대체. 이력 겸용 | 한 컬럼은 메시지·업로드·확정을 보호하지 못함 |
| R3 | correction 경로 | `POST /detections/{id}/correction`이 `serving_multiplier`만 곱해 `consumption_ratio`를 무시함(코드 확인). **기본값은 수정하지 않는다(P5).** 보완 패치(유효 배율로 재계산 + version 증가)는 **별도 커밋으로 준비만** 하고, **사용자 승인 후에만** 적용한다. 패치는 `ratio=1.0` 행에서 기존 동작과 같다. 승인 전에는 관찰·보고만 하고, 새 기능에서 어긋난 항목을 감지·안내한다(T18) | 다른 담당자의 공유 경로를 임의로 바꾸지 않기 위함 |
| R4 | 사진 분석 방식 | **기존 동기 `/meals/detect` 로직 재사용.** 단 업로드 저장과 분석 호출을 분리하고, 분석 실패 시에도 사진을 보존한다. 분석 큐·재시작 복구는 B | 기존은 한 요청에서 저장·YOLO(120초 제한)·DB를 처리하고 실패 시 파일을 삭제함 |
| R5 | 실시간 | A: 저장 성공 응답 직후 현재 화면 갱신 + 포커스 복귀·짧은 주기 재조회. B: SSE+outbox | 저장소에 SSE 전례 없음 |
| R6 | 휴대폰·"다른 기기" | **휴대폰 촬영 시연은 목표이며 S0(3.6장)로 먼저 검증한다.** 접속 위치 제한은 `LOCAL_TEST_IMAGE_ANALYSIS=true`일 때만 적용되고, 개발 서버 프록시를 거치면 백엔드에는 loopback으로 보인다(코드 실측). 휴대폰이 실제로 막히는 곳은 **요청 출처 검사(403)**이며 환경변수만으로 해소된다. S0 통과 시 휴대폰을 같은 Wi-Fi의 다른 기기로 검증하고, 실패 시 시연 구성 B·C로 대체하며 미검증을 표기한다 | 2026-10-13 프록시 헤더·검사 함수 실측(3.6장) |
| R7 | 비율 범위 | 0~1만. 1 초과("더 먹었어", "두 배")는 확인 질문 | 변경 없음 |
| R8 | 기준 배율 | `serving_multiplier`는 **기준 배율**로 불변. 정정은 CSV × 기준 배율 × 새 비율로 재계산 | 기존 CHECK(>0) 때문에 비율 0을 직접 저장 불가 |
| R9 | "섭취량" 표시 | **유효 배율** = 기준 배율 × 섭취 비율을 **새 채팅 화면의 카드·말풍선에서** 표시. 그램 값은 만들지 않고 CSV 단위 문구를 인용. **기존 화면은 수정하지 않는다**(비율 1.0이면 표시값 동일). 비율≠1 항목의 기존 화면 표시 반영은 팀 협의 과제 | 규칙: grams 미생성, P6 |
| R10 | 동일 request_id·다른 payload | 409 `request_id_conflict`, 쓰기 없음 | 유지 |
| R11 | 사진 입력·형식 | **카메라 촬영 가능.** 휴대폰은 `capture="environment"` 입력과 앨범 선택, PC는 파일 선택(웹캠 `getUserMedia`는 선택 사항이며 HTTPS·localhost에서만). 서버는 기존 정책대로 JPG/PNG만 허용하고 지원하지 않는 형식(HEIC 등)을 성공 처리하지 않는다. 휴대폰 접속은 R6·3.6장 S0로 검증 | 팀 목표(휴대폰 촬영 + 서버 분석) |
| R12 | 재학습 후보 | **우리 결정: 기존 `POST /meals`와 같은 규칙을 따른다.** 초안 수정·섭취량 수정·정정은 `RetrainingSample`을 만들지 않고, **확정 시점**에만 기존 규칙(동의한 사용자만, 최종 음식이 탐지 예측과 다를 때만)으로 만든다. 이를 위해 초안 항목에 **탐지 ID와 최종 음식 ID를 둘 다 보존**한다. 확정 서비스가 기존 규칙을 호출·재현하는 방식은 K17에서 정하고 T50으로 증명(경수 v6의 "보류"는 폐기) | 카메라 촬영·재학습 가능 방향 확정 |
| R13 | 완료 판정 | A0·A1·B를 각각 판정. 한쪽의 미완료가 다른 쪽의 완료 선언을 막지 않는다 | 다기기 미검증이 전체를 영구 미완료로 만드는 것을 방지 |
| R14 | 상호작용 | **대화가 유일한 입력 경로.** 섭취 비율 버튼·드롭다운·조정 패널·"이대로 저장하기" 버튼·음식 검색 UI를 만들지 않는다. 비율·확정·정정·취소·식사 종류는 모두 채팅 입력(텍스트)으로 한다. 선택지가 필요한 곳(5.3 표의 "답장 칩" 열: 음식 확인, 대상 불명확, 식사 종류, 저장 확인 등)에는 봇 말풍선 아래에 **탭하면 정해진 문장이 전송되는 답장 칩**을 둔다. 칩은 별도 API를 부르지 않고 **일반 사용자 메시지로 전송·저장**되며 서버 해석기를 그대로 거친다. 칩 문장은 8장 문법에 반드시 일치해야 한다 | 2026-10-14 사용자 지시: 조정 패널은 직접 올리기와 차이가 없음. 2026-10-15: 버튼식 선택지는 답장 칩으로 통일 |
| R15 | 자동 확정 규칙 | ① 저장은 **확정 의사가 해석됐을 때만** 한다. 말이 없으면 절대 저장하지 않는다. ② 확정 어휘는 2단계다. **명시적 저장 동사**(`올려줘·저장해줘·기록해줘` 등)는 저장 가능한 활성 초안이 있으면 유효하다. **단순 긍정**(`맞아·응·그래·좋아` 등)은 초안의 `pending_question`이 **`save_confirm`**(봇이 "~로 기록할까요?"라고 물은 상태)일 때만 저장으로 처리하고, 그 밖의 질문(예: "음식이 맞나요?")에 대한 단순 긍정은 그 질문에 대한 답으로만 처리한다(8장). ③ 한 문장에 비율과 저장 동사가 함께 있으면("절반만 먹었어 올려줘") 한 번에 처리한다. ④ 비율 없이 저장하면("맞아 올려줘") **기본 100%**. ⑤ 비율·대상·음식이 불명확하면 **저장하지 않고 되묻는다.** ⑥ 저장 전 봇 말풍선에는 **날짜·식사 종류를 항상 표시**한다(R18). ⑦ 저장 후에는 결과 카드로 알리고 섭취 비율은 말로 정정한다(5.2). 같은 확정 문장이 중복 전송돼도 Meal은 1개다(R2) | 자동 기록의 오작동 방지 |

## 2.5 기존 구현 범위 보호 (최우선 원칙)

이 기능은 다른 담당자의 구현 범위(인증·사진 분석·식단·추천·차트·관리자 QA·재학습 후보)에 **영향을 주지 않아야 한다.** 이 장이 다른 장과 충돌하면 이 장이 우선한다.

| 번호 | 원칙 | 구체 규칙 |
|---|---|---|
| P1 | 추가 우선 | 새 라우터·서비스·모델·컴포넌트·테스트는 **새 파일**로 만든다. 새 모델은 새 파일(예: `backend/app/models_chat.py`)에 둔다. 기존 파일 수정은 P2 목록으로 한정한다 |
| P2 | 수정 허용 목록 (연결에 필요한 최소분, **추가만**) | `backend/app/main.py`(새 라우터 등록, 플래그 뒤) · `backend/app/config.py`(설정 1개 추가) · `backend/app/models.py`(**A0:** `MealItem` 컬럼 2개 / **A1:** `Meal` 사진 연결 컬럼 1개 / 새 모델 파일의 메타데이터 등록 import 1줄) · `backend/app/services/analytics.py`(`meal_json` **키 추가만, 플래그 뒤**) · `frontend/src/main.jsx`·`MealHistory.jsx`(진입 버튼·라우팅, 플래그 뒤) · 신규 migration(A0·A1 별도 revision) · `ImageUpload` 등 그 밖의 기존 모델은 수정하지 않는다 · (사이드 메뉴에 "채팅으로 식사기록" 진입점이 기존 `Dashboard.jsx` 등에 있어야 하면 해당 파일에 **이 메뉴 항목 1개 추가만**, K20에서 위치 확인 후 보고. 기존에 없는 다른 메뉴 항목은 만들지 않는다). **이 목록 밖의 기존 파일을 고쳐야 하면 구현 전에 보고하고 승인을 기다린다** |
| P3 | 기능 플래그 | 새 설정 `CHAT_RECORD_ENABLED`(**기본 false**). false이면 새 라우트를 등록하지 않고 프론트 진입점을 숨기며 **`meal_json`에 새 키를 넣지 않는다.** 기존 API 응답은 변경 전과 완전히 같아야 한다(migration은 플래그와 무관하게 적용되므로 새 컬럼·테이블은 기본값으로 존재) |
| P4 | additive migration | 새 테이블 추가와 기존 테이블의 **기본값 있는 컬럼 추가**만 허용한다. 기존 컬럼·제약의 변경·삭제, 기존 행 데이터 갱신 금지. 기존 INSERT 경로(`POST /meals`, `seed_demo_meals`, `seed_foods`)가 **수정 없이** 계속 동작해야 한다 |
| P5 | 기존 함수 본문 비수정 | `save_meal`·`detect`·`correction`·`calculate_nutrition`·`apply_correction`·`recommend_meals` 등 기존 라우트·함수의 본문은 수정·리팩터링하지 않는다. 필요한 로직은 **새 서비스 함수**로 구현하고 기존 결과와 같음을 동등성 테스트로 증명한다. 생기는 중복 코드는 후속 통합 과제로 보고한다 |
| P6 | 응답 계약 보존 | 기존 API의 필드 제거·이름 변경·타입 변경 금지, **키 추가만** 허용. `consumption_ratio=1.0`인 기존 데이터에서 기존 화면의 표시값은 변경 전과 같아야 한다 |
| P7 | 집계 격리 | 초안·대화·첨부 테이블은 analytics·추천·차트·관리자 QA가 읽지 않는다. **확정된 Meal/MealItem만** 기존 경로로 흐른다 |
| P8 | 타 영역 영향은 보고만 | 추천(`비율 0` 항목이 "최근 먹은 음식"에 포함됨), Streamlit 차트(표시용 값만 전달), 관리자 QA(재학습 후보)에 미치는 영향을 K06에 기록한다. 해당 코드는 수정하지 않는다 |
| P9 | 회귀 증명 | 변경 전후 기존 테스트 전체·frontend build 결과를 비교하고, 기준 커밋 대비 `git diff --stat`을 첨부해 수정된 **기존 파일이 P2 목록 안**임을 보인다. 목록 밖이면 위반으로 보고한다 |
| P10 | 되돌리기 | 플래그 off + migration downgrade + 백업 복원으로 원상복구할 수 있어야 한다. 별도 브랜치에서만 작업한다 |

## 3. 착수 전 필수

1. `AGENTS.md` → `docs/rules/README.md` → `DEVELOPMENT_RULES.md` → `PENDING_DECISIONS.md` 순서로 읽는다. 규칙의 **명시적 금지·담당 범위와 충돌하는 작업만** 차단하고 보고한다. TEST-ONLY 주석은 규칙의 예외 허가가 아니다.
2. `git branch -r`로 실제 기준 브랜치와 **기준 커밋 해시**를 기록한다. README는 최초 클론 `develop`, 협업 방침 `main`으로 서술이 엇갈린다.
3. 별도 테스트 브랜치(예: `test/chatbot-record`)에서만 작업한다. migration은 R16을 따른다. 미커밋 변경은 보존한다.
4. 개인 로컬 DB와 테스트 계정(`test@calodetect.local`)만 사용한다. **DB와 `.private-uploads`를 쓰기 전에 함께 백업한다.** 더미 식단은 `python -m backend.scripts.seed_demo_meals`(개발 환경 전용)로 만든다.
5. 변경 전 기준 테스트를 실행해 기록한다. 기존 실패는 신규 실패와 구분한다.
   ```
   .\.venv-backend\Scripts\python.exe -m pytest backend/tests -q
   cd frontend; npm.cmd run build
   ```
   (README 기준 Backend 62개 통과·YOLO smoke 1개 제외는 참고값이며 고정 성공 조건이 아니다.)
6. **기준 응답 스냅샷을 저장한다.** 코드를 바꾸기 전에 테스트 계정·고정 데이터로 기존 API(`/meals/today`, `/meals/history`, `/analytics/today`, `/analytics/month`, `/recommendations/meals` 등 K07에서 확인한 엔드포인트)의 응답을 파일로 저장한다. T47·T49의 비교 기준이다.
7. 3.5장 확인표와 3.6장 S0를 채운 **착수 확인 보고서**를 먼저 제출한다. A1 전용 항목(K14 일부, K15~K17)은 A1 착수 시 다시 확인해도 된다.

**판정 후 규칙** — 차단: 그 항목에 의존하는 작업만 멈추고 근거·대안을 보고, 독립 작업은 계속한다. 대응 가능: 정책을 유지하는 대응을 기록하고 진행한다. 제한: 독립 기능은 검증하되 통합 완료를 선언하지 않는다. 차단되지 않은 작업은 추가 확인을 기다리지 않고 진행한다.

### 3.6 휴대폰 촬영 시연 사전 검증 S0 (코드 수정 없음, A0·A1 착수와 병행 가능)

**목적:** 휴대폰으로 촬영한 사진이 서버 PC에서 분석·저장되는 경로가 **기존 앱 그대로** 되는지 먼저 확인한다. 기존 코드·`.env`는 수정하지 않고 터미널 환경변수와 실행 옵션만 바꾼다(환경변수가 `.env`보다 우선한다).

**실측으로 확인된 사실 (저장소 `accounts.py`·`api.py`의 실제 함수와 `http-proxy` 1.18.1로 재현. Vite 7 프록시는 같은 기본값을 쓸 것으로 보이나 S0에서 재확인)**

| 설정 | 휴대폰(LAN 주소 접속) | PC(localhost 접속) |
|---|---|---|
| 기본값: `FRONTEND_ORIGIN=localhost`, 플래그 켬 | 출처 검사 **403** | 통과 |
| `FRONTEND_ORIGIN=localhost`, 플래그 끔 | 출처 검사 **403** | 통과 |
| `FRONTEND_ORIGIN=LAN주소`, 플래그 켬 | 출처 통과, 이미지 환경 **503** | 403 |
| **`FRONTEND_ORIGIN=LAN주소`, 플래그 끔** | **모두 통과** | 출처 **403** (PC도 LAN 주소로 접속) |

- 개발 서버 프록시를 거치면 백엔드에는 Host가 loopback으로 바뀌고 전달 헤더(X-Forwarded-For 등)가 없으며 Origin은 브라우저가 보낸 값 그대로 도착한다. 그래서 "loopback 접속 검사"는 휴대폰도 통과하고, 막는 것은 **Origin 불일치(403)**와 **`FRONTEND_ORIGIN`이 LAN 주소일 때 로컬 개발 환경 판정 실패(플래그가 켜져 있으면 503)**다.
- 프록시 없이 휴대폰이 백엔드에 직접 붙거나, 터널·리버스 프록시처럼 `X-Forwarded-For`가 붙으면 플래그가 켜진 상태에서는 막힌다.

**1순위 구성 (시연 구성 A: 같은 Wi-Fi의 휴대폰 → PC 개발 서버)**
```
# 터미널 A (백엔드): .env는 건드리지 않고 환경변수로 덮어쓴다
$env:APP_ENV='development'
$env:FRONTEND_ORIGIN='http://<PC의 LAN IP>:5174'
$env:LOCAL_TEST_IMAGE_ANALYSIS='false'
$env:IMAGE_STORAGE_DIR='.private-uploads'
.\.venv-backend\Scripts\python.exe -m uvicorn backend.app.main:app --host ::1 --port 8000

# 터미널 B (프론트)
$env:CALODETECT_API_TARGET='http://[::1]:8000'
npm.cmd run dev -- --host 0.0.0.0 --port 5174     # 옵션 중복 오류 시: npx vite --host 0.0.0.0 --port 5174
```
- **이 구성의 의미:** `LOCAL_TEST_IMAGE_ANALYSIS=false`는 코드 우회가 아니지만, 팀이 걸어 둔 **사진 분석 접속 위치 제한을 설정으로 끄는 것**이다. 이 상태에서 개발 서버를 같은 Wi-Fi에 연다. 따라서 아래 제한을 지키고, 시연 전 이 설정을 쓴다는 사실을 사진 분석 담당자에게 공유한다.
- 백엔드는 계속 `::1`에서만 열고 휴대폰은 프론트(5174)로만 접속한다. Windows 방화벽은 사설망 프로필의 TCP 5174만 열고, **허용 원격 주소를 시연 휴대폰의 IP로 제한**한다(예: `New-NetFirewallRule -Direction Inbound -Protocol TCP -LocalPort 5174 -RemoteAddress <휴대폰 IP> -Profile Private -Action Allow`).
- 접속은 **IP 주소**로 한다(호스트 이름은 Vite의 호스트 허용 검사에 걸릴 수 있다). PC 브라우저도 같은 LAN 주소로 접속한다.
- Google 로그인은 LAN 주소가 등록되어 있지 않으므로 **이메일 테스트 계정**으로 로그인한다. 더미 식단 시드는 `FRONTEND_ORIGIN`을 바꾸기 **전에** 실행한다.

**검증 항목 (모두 기록)**

| 번호 | 확인 | 통과 기준 |
|---|---|---|
| S0-1 | 휴대폰에서 LAN 주소 접속·테스트 계정 로그인 | 로그인 성공(403·연결 실패 아님) |
| S0-2 | "사진 바로 찍기" 동작(휴대폰은 `capture` 입력 방식, HTTPS 불필요. 아이패드는 PC로 분류되어 사진 선택으로 대체될 수 있음) | 카메라가 열리고 파일이 선택됨 |
| S0-3 | 업로드·분석 `POST /meals/detect` | 200, 서버 `.private-uploads`에 파일과 `image_uploads`·`detection_logs` 행 생성 |
| S0-4 | 분석 소요 시간(모델을 요청마다 새로 로드하며 120초 제한) | 시연 허용 범위 이내 기록 |
| S0-5 | 저장된 사진 재조회·재로그인 후 조회 | 휴대폰에서 이미지 표시 |
| S0-6 | 형식·해상도: 기본 해상도 촬영, 고해상도(약 5천만 화소) 모드, 아이폰 HEIC | 서버 기준(JPG/PNG·10MB·2500만 화소) 초과 시 실패 원인 기록 |

**판정과 대체 구성**

| 결과 | 조치 |
|---|---|
| 모두 통과 | **시연 구성 A 확정.** R6의 "다른 기기" 검증을 같은 Wi-Fi 휴대폰으로 진행 |
| S0-1 실패(접속 불가) | 공용·게스트 Wi-Fi의 기기 간 통신 차단이 흔한 원인. 휴대폰 핫스팟에 PC를 연결하거나 PC 핫스팟을 쓴다(**시연 구성 B**). 방화벽 규칙도 확인 |
| S0-1 403 | 환경변수 적용 여부(`FRONTEND_ORIGIN`이 접속 주소와 정확히 같은지, 포트 포함) 확인 |
| S0-3 503 | `IMAGE_STORAGE_DIR` 설정 또는 플래그 값 확인 |
| S0-6 실패 | 촬영 해상도를 낮추거나, 채팅 업로드에서 클라이언트 리사이즈를 적용(7장) |
| 위가 모두 불가 | **시연 구성 C**: 휴대폰으로 촬영해 PC로 전송(메신저·케이블)한 뒤 PC에서 사진 선택. 서버 분석·저장·대화 흐름은 동일하게 시연하되 "휴대폰 직접 업로드 미검증"으로 표기 |
| 외부 접속(터널·클라우드 배포) 필요 | **팀 결정 사항.** 이미지 보관 정책이 미확정이고 개발 서버를 외부에 노출하게 되므로 개인 테스트 범위 밖. 기존 Docker 이미지에는 YOLO 의존성이 포함되어 있어 배포 시 분석 자체는 가능하나 HTTPS·보관 정책·접근 제어 결정이 선행되어야 함 |

- 이 설정은 개인 테스트 PC의 로컬 환경에서만 쓰며 커밋하지 않는다. 테스트 후 환경변수를 되돌리고 방화벽 규칙을 제거한다. 테스트 계정과 음식 사진만 사용한다.
- 시연 전날 같은 장소·같은 네트워크·같은 기기로 S0를 한 번 더 리허설한다.

## 5. 화면 명세와 사용자 흐름

### 5.0 화면 명세 (시안에서 조정 패널만 제외)

**웹(데스크톱·노트북): 사이드 메뉴 + 채팅 + 우측 요약 (시안의 가운데 "분석된 음식" 패널 제외)**

| 영역 | 내용 | 데이터 출처 |
|---|---|---|
| 사이드 메뉴 | 기존 메뉴 그대로 + **채팅으로 식사기록**(신규 1개, 플래그 뒤). 시안의 다른 메뉴(설정·도움말 등)가 기존에 없으면 만들지 않는다 | 기존 메뉴에 항목 1개 추가만(P2·K20) |
| 채팅(넓게) | 제목 "채팅으로 식사 기록하기", 날짜 구분선, 봇 인사 → 내 사진 메시지 → 봇 분석 결과 말풍선 + **음식 카드(읽기 전용: 사진 조각·이름·kcal·비율 표시)** → 입력창(사진 아이콘·**사진 찍기**·**앨범에서 선택**·텍스트·전송) → 사용자 발화 → 봇 "기록했어요" 카드 | 대화·메시지·첨부·초안(서버) |
| 우측 요약 | **오늘의 식사**(섭취/목표 kcal 도넛) + **최근 식사 히스토리**. 자동 저장 직후 갱신 | **기존 API를 읽기만**(`analytics/today`, 기존 식사 목록). `DailyHome.jsx`·`MealHistory.jsx` 무수정 |

- 시안의 "분석된 음식" 패널(원본 사진·비율 버튼·예상 영양 정보·이대로 저장하기·재분석)은 **구현하지 않는다.** 원본 사진은 채팅의 사진 메시지로 보이고, 영양 합계는 봇 말풍선 카드에 텍스트로 보인다. 재분석은 채팅에서 "다시 분석해줘" 또는 새 사진 전송으로 대신한다(A0·A1는 새 사진만).
- 음식 카드의 **비율 표시는 읽기 전용 배지**다(처음 100%, 사용자가 말하면 해당 카드가 50% 등으로 바뀐다). 카드를 눌러 값을 바꾸는 동작은 없다.

**모바일(세로): 시안의 ③분석 결과·④섭취량 조정 화면 없이 채팅 한 화면에서 진행**

| 단계 | 화면 |
|---|---|
| ① 시작 | 기존 랜딩·로그인 재사용(이미 로그인이면 건너뜀). 진입 버튼만 연결 |
| ② 채팅 | 인사 → **[📷 사진 찍기] [앨범에서 선택]** + 입력창 → 사진 메시지 → 분석 결과 말풍선(음식 카드·합계) → 사용자 발화 → 저장 완료 카드(채팅 안) |
| ③ 저장 완료 | 채팅 안의 완료 카드(체크, "식사 기록이 저장되었어요!", 식사 카드, **[다른 사진도 기록하기] [오늘의 식사 보기]**). 두 버튼은 새 초안 시작 / 오늘 화면 이동이며 식사 데이터를 바꾸지 않는다 |
| ④ 오늘의 식사 | 기존 오늘 화면으로 이동(저장 직후 갱신 확인) |

**동작 규칙**
- **저장은 대화로만 일어난다.** 서버는 사용자 메시지를 해석해(8장) 확정 의사가 있을 때만 초안을 식사로 확정한다. 클라이언트에 저장 버튼이 없고, 클라이언트가 영양값·확정 요청을 직접 보내는 경로도 없다(확정은 메시지 처리 안의 서버 서비스 호출).
- 봇 분석 말풍선은 **음식·항목별 kcal·합계·날짜·식사 종류를 보여 주고 다음 행동을 안내**한다. 예: "갈비구이, 밥으로 분석됐어요(합계 약 723 kcal) · **오늘 저녁**. 얼마나 드셨는지 말씀해 주세요. 다 드셨으면 \"올려줘\"라고 하시면 바로 기록해요." 이때 `pending_question = amount`이며, 단순 긍정("응")은 저장하지 않는다(R15).
- 분석 말풍선과 저장 확인 말풍선 아래에는 **식사 종류 답장 칩**(기존 "식단 올리기"와 같은 선택지, K20)을 둔다. 현재 선택값은 강조 표시한다. 칩을 누르면 "점심으로 바꿔줘"가 전송되고 초안의 식사 종류만 바뀐다(저장 안 됨).
- 식사 종류 기본값: 기존 화면에 시각 규칙이 있으면 그 규칙을 쓰고, 없으면 05:00–10:59 아침 / 11:00–15:59 점심 / 16:00–21:59 저녁 / 그 외는 기존 선택지의 네 번째 값(야식 또는 간식). Asia/Seoul 기준.
- 사용자가 비율만 말하면("절반만 먹었어") 카드·합계를 갱신하고 "**오늘 저녁**, 갈비구이 절반(약 362 kcal)으로 기록할까요?"라고 되묻는다(`pending_question = save_confirm`, 저장 안 됨). 비율+저장 동사를 함께 말하면 즉시 저장한다(R15).
- 저장 완료 카드는 당시 확정 내용의 snapshot이며 이후 정정해도 과거 말풍선은 바뀌지 않는다(11장).
- 항목 kcal·합계·탄단지는 **서버가 계산**한 값을 표시한다. 시안의 수치(총 675 kcal 등)는 **예시**이므로 하드코딩하지 않는다.
- 탄수화물·단백질·지방은 g과 섭취 비율(%)로만 표시한다(`macro_targets` null, 목표 대비 % 금지).
- 음식 카드 사진 조각은 탐지 `bbox`로 원본을 잘라 표시한다(`bbox` 없는 수동 선택 음식은 이름만).
- 분석 중·실패·인식 0건은 채팅 말풍선으로 안내하고("다시 찍거나 음식 이름을 말씀해 주세요") 사진은 보존한다. 음식 이름은 150종 카탈로그와 **정확히 일치**할 때만 초안에 추가한다(8장). 음식 검색 UI는 만들지 않는다(R14).
- 채팅으로 기록하는 식사의 기준 배율은 1.0이다(R17). 음식 카드에는 "CSV 단위 문구 × 섭취 비율"로 표시한다(예: `인분 (약 200g) · 50%`).
- 반응형: 좁은 폭에서는 우측 요약을 숨긴다. 기존 앱의 색·글꼴 토큰을 재사용하고 새 전역 CSS는 신규 파일에 한정한다(P1).

### 5.1 (A0) 확정 식사 섭취량 수정 — 말로 수정
1. `MealHistory.jsx` 항목 행의 **"챗으로 수정"** 진입점 → 해당 `item_id`의 작은 입력창(인라인 또는 모달)을 연다. **비율 버튼·저장 버튼은 두지 않는다**(R14). 입력창에는 안내문과 텍스트 입력, 해석 결과 표시만 있다.
2. 사용자가 "절반만 먹었어"를 입력한다. 클라이언트는 `interpret`를 호출하고, 결과가 `update_consumption`이면 `preview`를 호출해 **수정 전·후 6개 영양값**을 보여 주고 "이렇게 바꿀까요?"라고 되묻는다. 확정 발화 없이는 확정 식사가 변하지 않는다.
3. **A0는 대화를 서버에 저장하지 않으므로 클라이언트가 직전 미리보기를 보관한다.**
   - 보관 값: `item_id`, `consumption_ratio`, 미리보기 응답의 `version`(→ `expected_version`), `request_id`.
   - `request_id`는 **미리보기가 새로 확정될 때마다** `crypto.randomUUID()`(없으면 `crypto.getRandomValues` 기반 UUID v4)로 새로 만들고, 같은 미리보기의 저장 재시도에는 같은 값을 쓴다.
   - 사용자가 "저장해줘"·"응" 등을 입력하면 `interpret` 결과가 `confirm_save`일 때만, 보관한 값으로 `PUT .../consumption`을 호출한다. 보관한 미리보기가 없으면 저장하지 않고 "어느 정도 드셨는지 먼저 말씀해 주세요"라고 안내한다. (A0 입력창에서는 직전 봇 질문이 항상 "이렇게 바꿀까요?"이므로 미리보기가 있으면 `pending_question = save_confirm`으로 간주한다.)
   - "절반만 먹었어 저장해줘"처럼 한 문장이면(`update_and_confirm`) 미리보기를 내부적으로 만든 뒤 같은 요청 흐름에서 바로 PUT 한다(R15).
   - 새 비율을 말하면 보관한 미리보기를 버리고 새로 만든다. 저장 후 보관 값을 비우고 히스토리·오늘을 재조회한다.
   - 이 규칙은 A0 전용이다. A1에서는 확정 요청을 클라이언트가 보내지 않는다(5.0 동작 규칙).
4. "아니, 4분의 1"로 다시 말하면 기준 배율에서 재계산한다(이중 적용 없음). 저장 후 대화 원문·변경 결과·이력은 보존한다(A1에서는 대화로 저장, A0 입력창은 대화를 저장하지 않는다, R1).

### 5.2 (A1) 사진으로 새 식사 기록 (자동 기록)
1. 채팅에서 **사진 촬영**(휴대폰 카메라) 또는 **앨범·파일 선택**. 거부·취소·미지원이면 앨범·파일 선택으로 이어진다. 취소하면 서버 기록을 만들지 않는다.
2. 업로드. 성공하면 사진 메시지와 첨부를 서버에 저장한다.
3. 분석 실행(동기). 진행·실패·완료를 말풍선으로 표시하고 서버가 **초안(음식·기준 배율 1.0·비율 100%·날짜 오늘·식사 종류 기본값)** 을 만든다(R17·R18).
4. 봇이 음식·kcal·합계·날짜·식사 종류를 보여 주고 섭취량을 묻는다(식사 종류 칩 표시). 음식이 틀리면 사용자가 말로 고친다(예: "갈비구이가 아니라 불고기야", 150종 정확 일치만 허용 — 8장).
5. 사용자가 비율을 말한다("절반만 먹었어"). 서버가 초안을 갱신하고 봇이 확인한다. 확정 의사가 포함돼 있으면 6으로 간다.
6. 사용자가 확정 의사를 말한다("올려줘", 또는 저장 확인 질문 뒤의 "응"). 서버가 초안을 **원자적으로 식사로 확정**한다. 날짜·식사 종류는 초안 값(기본값 또는 칩·말로 바꾼 값)을 쓴다("어제 저녁으로 올려줘"처럼 한 문장도 가능, 8장). **저장 후에는 날짜·식사 종류·음식을 바꿀 수 없으므로** 저장 전 말풍선에 항상 표시한다(R18).
7. 사진·초안 항목과 확정 Meal/MealItem을 연결하고, 봇이 완료 카드로 알리며, 우측 요약·히스토리·오늘·월간에 반영한다.
8. 저장 후 정정은 5.1과 같은 방식으로 말로 한다. "챗으로 수정"은 연결된 대화로 이동하거나 식사 연결 대화를 만든다.

### 5.3 대화 문구와 답장 칩

정상 흐름의 봇 말풍선은 **인사 → 분석 결과(섭취량 질문 포함) → (필요 시 저장 확인) → 저장 완료**이며, 질문을 연달아 던지지 않는다. 아래 표는 확인·예외·오류 상황의 문구다.

- **답장 칩**은 탭하면 "칩 전송 문장" 열의 문장이 **일반 사용자 메시지로 전송**된다(R14). 칩 전송 문장은 8장 문법과 반드시 일치해야 하며, 테스트(T67)로 확인한다.
- `pending_question` 열은 그 말풍선을 보낸 뒤 초안에 기록하는 상태다(8장). 단순 긍정("맞아·응")은 이 상태에 대한 답으로 해석한다.
- 음식 검색 UI·별도 버튼은 만들지 않는다.

## 6. 저장 구조와 상태

논리 모델이며 기존 테이블·ID 타입을 조사해 **최소 구조**로 매핑한다. 표의 각 행이 별도 테이블일 필요는 없다.

| 대상 | 필요한 데이터·제약 | 단계 |
|---|---|---|
| Conversation | id, user_id, created_at, updated_at, 상태 | A1 |
| Message | conversation_id, author_role, 원문/표시 내용, client_message_id, 대화별 server sequence, status, created_at, reply_to/action 연결. (user, conversation, client_message_id) unique | A1 |
| ChatAttachment(신규) | **기존 `ImageUpload`를 수정하지 않고 참조**: image_upload_id(FK, nullable — 업로드 완료 전), conversation/message 연결, MIME, size, checksum, 업로드 상태, upload_request_id, 서버 생성 저장 키. 브라우저 object URL·만료 URL만 저장하지 않음 | A1 |
| MealDraft | conversation_id, 첨부, status, version, meal_date, meal_type(K20의 기존 저장값), **pending_question**(`none / amount / food_check / food_name / target / save_confirm`), **pending_target_id**(대상 칩 선택 후 비율 대기 시), confirmed_meal_id nullable(**unique**) | A1 |
| DraftItem | draft_id, 안정 id, **source_detection_id(nullable)와 최종 food_id 둘 다 보존**(R12), 기준 배율(채팅 기록은 1.0 고정, R17), 섭취 비율, 서버 계산 nutrition, 확인 상태 | A1 |
| MealItem(기존) | `consumption_ratio` Float NOT NULL 기본 1.0 CHECK 0~1, `version` Integer NOT NULL 기본 1 | A0 |
| MutationRequest | user_id, operation, request_id, **(user_id, operation, request_id) unique**, target 종류·ID, 정규화 payload hash, 결과 상태·결과 ID·결과 version, 성공한 변경의 before/after(이력 겸용), 시각 | A0 |
| Meal(기존) | nullable `chat_attachment_id`(사진 연결). 초안 항목과 안정적 연결 | A1 |
| ChangeEvent | 사용자 범위 변경 id, 대상 id·version, 타입, 커밋 시각(outbox) | B |
| AnalysisJob | 첨부, 상태, 결과/오류 코드, attempt, 시각 | B |

- `serving_multiplier`는 기준 배율로 **불변**. 유효 배율 = `serving_multiplier × consumption_ratio`.
- SQLite 테스트가 `create_all`을 쓰므로 CHECK·기본값·unique를 **모델에도 선언**한다. 새 모델은 새 모델 파일에 둔다(P1). SQLAlchemy `version_id_col`은 쓰지 않는다(수동 증가).
- 초안 상태: `pending_upload → analyzing → needs_confirmation → ready → confirmed`, 별도로 `failed/retryable`, `abandoned`.
- 확정은 허용된 상태에서만 가능하다. 분석 미완료·대상 미확정·업로드 미완료이면 확정하지 않는다. 분석 실패 후 직접 음식 선택으로 초안을 완성할 수 있고, 실패 사실은 남긴다.
- 업로드 전에 취소한 촬영은 서버 기록을 만들지 않는다. 저장된 초안을 중단하면 `abandoned`로 보존하고 집계에서 제외한다.
- 초안은 서버 영양값을 갖지만 **집계에는 포함하지 않는다.** 집계는 확정된 Meal/MealItem만 반영한다.
- 사진이 있는 Meal은 nullable `detection_log_id`에만 의존하지 않고 첨부와 연결한다. `meal_json`은 기존 탐지 기반 이미지 URL을 **그대로 유지**하고, 플래그 on이며 첨부 연결이 있을 때만 이미지를 **추가**한다(수동 선택·분석 실패 후 저장에서도 사진이 보이게).
- 한 초안은 최대 한 Meal로 확정된다(DB unique). 다른 request_id로 두 번 확정해도 Meal은 1개다.
- 활성 초안은 대화당 1개. 새 사진은 새 식사 초안을 명시적으로 시작하며 저장된 식사를 덮어쓰지 않는다.
- 메시지 순서는 server sequence로 정하고(시간값 불사용) 커서 기반 페이지네이션을 제공한다.
- 재로그인·다른 탭에서는 서버 상태를 복원한다. localStorage·브라우저 메모리로 영속성을 대체하지 않는다.
- 서버에 도착하지 않은 메시지는 전송 완료로 표시하지 않고 실패·재시도 상태로 구분한다.

## 7. 사진 저장·분석과 실패 복구

- 기존 영속 이미지 저장(`IMAGE_STORAGE_DIR`)과 소유권 검증 조회를 재사용한다. 이 설정은 **이미지 보관 정책 확정이 아니다**(`PENDING_DECISIONS.md` 미확정). 테스트 사진만 사용한다.
- 업로드 검증은 기존 정책을 따른다(실제 디코딩, JPG/PNG, 10MB, 2500만 화소). 경로는 서버가 생성하고 원래 파일명을 쓰지 않는다. 지원하지 않는 형식(HEIC 등)을 성공 처리하지 않고 지원 형식 선택을 안내한다.
- **업로드 저장과 분석을 분리한다**: ① 사진 저장·첨부·메시지 커밋 → ② 분석 호출(기존 `detect_image`) → ③ 결과 저장·초안 생성. 기존 `/meals/detect`처럼 분석 실패 시 파일을 삭제하지 않는다. 기존 `/meals/detect` 본문은 **수정하지 않는다**(P5). 새 서비스에서 기존 `detect_image`를 호출한다. 업로드 검증(JPG/PNG·10MB·2500만 화소·디코딩)은 K16에 따라 **기존 검증 함수가 호출 가능하면 그대로 호출**하고, 라우트 본문에 직접 들어 있어 호출할 수 없을 때만 같은 기준으로 새 코드에 구현해 동등성 테스트(T50)로 증명한다.
- 파일 저장과 DB는 원자적이지 않다. 임시 업로드 → 파일 완결 → 첨부 uploaded 기록 순서와 실패 보상을 구현한다. DB 실패 뒤 남은 고아 파일은 참조 여부를 확인해 정리하고, **참조 중인 사진은 절대 삭제하지 않는다.** (유예 기간 정책은 B)
- 분석 결과는 성공 시 DB에 저장하고 새로고침마다 재분석하지 않는다. 분석 재시도는 같은 첨부에 연결한다.
- 이미지가 없으면 깨진 이미지만 남기지 말고 로드 실패·다시 시도 상태를 보여준다.
- 사진을 LLM 등 외부 서비스에 보내지 않는다.
- **휴대폰 촬영 대응(신규 채팅 업로드 컴포넌트에만 적용, 기존 `PhotoInput.jsx` 수정 금지):** `accept="image/jpeg,image/png"`와 `capture="environment"` 입력을 쓰고, 업로드 전에 브라우저에서 긴 변 2048px 이하로 축소해 JPEG로 변환한다(10MB·2500만 화소 초과와 HEIC 방지). 변환 실패 시 원본을 그대로 보내지 않고 안내한다. 서버 검증 기준은 변경하지 않는다.
- **B:** 분석 작업을 durable job으로 바꾸고, 서버 재시작 시 pending/processing을 재실행하거나 retryable로 전환한다. 오래된 분석 응답이 사용자 정정이나 새 attempt 결과를 덮어쓰지 않도록 attempt/version을 확인한다.

## 8. 대화 해석 (유일한 입력 경로, R14·R15)

채팅 입력을 비율·확정·정정·취소 의도로 바꾼다. **이 해석이 기능의 핵심**이므로 화면과 함께 먼저 구현한다. 확정 의사는 서버가 해석한 결과로만 인정한다.

### 8.1 확정·긍정·취소 어휘와 대화 상태

| 구분 | 어휘(정규화 후, 끝 `요` 허용) | 유효 조건 | 결과 |
|---|---|---|---|
| **명시적 저장 동사** | `올려줘, 올려, 저장해줘, 저장해, 기록해줘, 기록해` | 저장 가능한 활성 초안이 있음(A0는 보관한 미리보기가 있음) | 저장 |
| **단순 긍정** | `맞아, 응, 그래, 좋아, 네, 어` | `pending_question`에 따라 다름(아래) | 아래 표 |
| **취소** | `취소, 그만, 안할래`, 그리고 정정 접두어 제거 후 **남는 내용이 없는** `아니야/아니/아냐` | 활성 초안 또는 미리보기가 있음 | 저장 없음. 초안은 `abandoned`가 아니라 **현재 상태로 보존**하고 `pending_question = none`(사진·초안 유지, 다시 말하면 이어서 진행). 초안을 버리려면 새 사진을 보낸다 |

단순 긍정의 해석(`pending_question` 기준):

| pending_question | 직전 봇 질문 | "맞아·응" 등의 의미 |
|---|---|---|
| `save_confirm` | "~로 기록할까요?" | **저장** |
| `food_check` | "음식이 맞나요?" | 음식 확정만. 저장하지 않고 섭취량 질문으로 이동(`amount`) |
| `amount` | "얼마나 드셨는지 말씀해 주세요" | **저장하지 않는다.** "다 드셨으면 '다 먹었어 올려줘'라고 말씀해 주세요"로 안내 |
| `none`·`food_name`·`target` | — | 저장하지 않고 직전 질문을 다시 안내 |

- 해석기는 순수 함수로 `(text, pending_question, 현재 대상 목록, 허용 음식명·식사 종류 목록)`을 입력받는다. DB는 대화 서비스가 읽어 넘긴다.
- **결합 문장:** `[비율 문장] [식사 정보]? [저장 동사]` 순서로 공백·쉼표 구분을 허용한다(예: "절반만 먹었어 올려줘", "4분의 1, 저장해줘", "절반만 먹었어 어제 저녁으로 올려줘"). 모든 부분이 각 문법에 전체 일치할 때만 처리한다. 저장 동사만 있으면 기본 100%.
- 단순 긍정과 비율의 결합("응 절반")은 지원하지 않는다(확인 질문).

### 8.2 음식 정정 (A1 초안 전용)

```text
형식: [음식A]가|이 아니라 [음식B]야|이야|예요|이에요      예) "갈비구이가 아니라 불고기야"
      [음식B]야|이야 (pending_question = food_name 또는 대상이 하나뿐인 food_check일 때만)
```
- 음식A는 현재 초안의 음식명과, 음식B는 **150종 카탈로그의 food_name과 정확히 일치**해야 한다(공백 제거 후, `_`는 `/`·공백과 같게 취급: "곰탕 설렁탕" = `곰탕_설렁탕`). 별칭·유사도·부분 일치 금지.
- 일치하지 않으면 바꾸지 않고 "음식 이름 불일치" 문구(5.3)로 되묻는다.
- 정정하면 해당 DraftItem의 food_id를 바꾸고 기준 배율 1.0·현재 섭취 비율로 영양값을 다시 계산한다. source_detection_id는 유지한다(R12). 저장 후 음식 변경은 지원하지 않는다(R18).

### 8.3 날짜·식사 종류

```text
날짜: 오늘 | 어제                          (그 밖의 날짜 표현은 확인 질문)
식사 종류: K20에서 확인한 기존 선택지의 표시명과 정확히 일치 (예: 아침 | 점심 | 저녁 | 야식)
형식: [날짜]? [식사 종류](으)로 (바꿔줘|해줘|올려줘|저장해줘|기록해줘)?
      예) "점심으로 바꿔줘", "어제 저녁으로", "어제 저녁으로 올려줘"
```
- 저장 동사가 붙으면 식사 정보를 바꾼 뒤 저장한다. 없으면 바꾸기만 하고 "~로 기록할까요?"로 되묻는다(`save_confirm`).
- 식사 종류 칩은 "{표시명}으로 바꿔줘"를 전송한다.
- 저장 후 변경은 지원하지 않는다(R18, 5.3 문구).

### 8.4 비율 표현

`backend/app/services/consumption.py`에 **순수 함수**로 구현한다(DB·네트워크 의존 없음). 이를 호출하는 대화 서비스가 상태를 저장한다. 해석기는 LLM 어댑터로 교체 가능한 인터페이스로 분리한다.

**정규화 (입력과 허용 표현 양쪽에 동일 적용)**
1. 공백을 모두 제거한다("4분의 1" = "4분의1").
2. 문장 끝의 `.` `!` `~`를 제거한다.
3. 앞머리 정정 표현을 긴 것부터 **정확히 한 번** 제거한다: `아니야`, `아니`, `아냐`, `정정`. 바로 뒤 쉼표 하나도 제거한다.
4. 3에서 접두어를 제거한 뒤 **남는 내용이 없으면 취소**(8.1)로 처리한다. 남는 내용이 있으면 정정 문장으로 계속 해석한다("아니, 4분의 1" → 0.25).

**매칭:** 정규화된 문자열이 "핵심어 + 어미" 조합과 **전체 일치**할 때만 확정한다(부분 검색 금지). 어미: `먹었어`, `먹었어요`, `먹음`, `먹었음`.

| 비율 | 핵심어 | 어미 없이 단독 허용 |
|---|---|---|
| 1.0 | 다, 전부 | 아니오 |
| 0.5 | 절반, 절반만, 반만, 1/2, 50% | 예 |
| 0.5 | 반 | 아니오("반 먹었어") |
| 0.25 | 4분의1, 사분의일, 1/4, 25% | 예 |
| 0.75 | 4분의3, 사분의삼, 3/4, 75% | 예 |
| 0.0 | 안, 하나도안 | 아니오 |

**전체 적용 접두어:** `전부`·`다`·`모두` 뒤에 비율 문장이 오면 초안의 모든 음식에 적용한다(예: "전부 절반만 먹었어" → 모든 음식 0.5). `다 먹었어`·`전부 먹었어`는 그 자체가 1.0이며, 대상이 여럿이면 모든 음식 1.0으로 처리한다. 대상 없이 "절반만 먹었어"처럼 전체 접두어 없는 비율은 음식이 여럿이면 `ambiguous_target`.

- 확정 예: "3/4 먹었어", "절반", "반 먹었어", "다 먹음", "아니, 4분의 1", "하나도 안 먹었어요", "전부 절반만 먹었어".
- 확인 질문 예: "조금", "반쯤", "더 먹었어", "반 남겼어", "반찬만 먹었어", "반도 못 먹었어", "다 못 먹었어", "150%", "125%", "50%가 아니라 25%", "절반보다 적게 먹었어", "50%~75%", "1/4.5", "2인분 먹었어", "두 그릇"(기준 배율 표현, R17), "응 절반".
- 허용 표현을 늘릴 때는 테스트도 함께 추가한다.

**반환 구조**
```json
{"intent":"update_consumption|confirm_save|update_and_confirm|affirm|change_food|set_meal_info|cancel|clarify",
 "meal_info":{"date":"today|yesterday|null","meal_type":"<K20 저장값>|null"},
 "food_change":{"from_food_id":"...|null","to_food_id":"...|null"},
 "target_type":"draft_item|meal_item|null","target_id":"...|null",
 "consumption_ratio":0.5,"needs_clarification":false,
 "clarification_reason":"unsupported_expression|ambiguous_target|missing_target|empty_meal|null",
 "candidates":[{"id":"...","food_name":"..."}],"source":"rule"}
```
모든 clarify 응답은 `consumption_ratio=null`, `needs_clarification=true`. `affirm`은 단순 긍정이며, 저장 여부는 대화 서비스가 `pending_question`으로 결정한다(8.1).

### 8.5 대상 결정
- 클릭한 카드의 `draft_item_id` 또는 `meal_item_id`를 우선하되 소유권·대화·초안/식사 관계를 검증한다. 불일치·없음·타 사용자 → **404**.
- 텍스트의 **현재 대상 목록 안 정확한 음식명**(+제한된 조사, 예: "밥은 절반만 먹었어")을 식별한 뒤 남은 비율 문장을 전체 매칭한다. 일치 대상이 **하나일 때만** 선택한다. 별칭 추측·유사도 선택·새 음식 생성 금지. 음식명과 카드 대상이 충돌하면 질문.
- 식사 단위 진입: 항목 0개 → `empty_meal`, 1개 → 자동 선택, 2개 이상 → `ambiguous_target` + 후보(소유 항목만). 대상이 전혀 없으면 `missing_target`.
- **여러 음식을 한 문장에서 말할 수 있다**: 쉼표·"그리고"로 나눈 각 절이 `음식명 + 비율`로 **모두** 전체 일치할 때만 한 번에 적용한다(예: "밥은 절반, 불고기는 다 먹었어"). 하나라도 불명확하면 아무것도 적용하지 않고 되묻는다. `전부 절반만 먹었어`·`다 먹었어`처럼 **전체 키워드**가 있으면 초안의 모든 음식에 적용한다. 음식이 여럿인데 대상 없이 "절반만 먹었어"라고만 하면 대상을 되묻는다(`ambiguous_target`, 후보 칩 허용).
- 대상 칩("갈비구이는")만 전송되면 `pending_target_id`에 저장하고 `pending_question = amount`로 비율을 기다린다. 다음 비율 문장은 그 대상에 적용한다.
- "아니 4분의 1"은 서버에 저장된 현재 대상이 **유일하고 version이 유효할 때만** 연결한다.
- 초안의 음식을 다시 고르면 기준 단위와 배율을 다시 확인한다.

## 9. 계산

```
base      = serving_multiplier            # 불변(초안 단계에서는 사용자 확인 전까지 변경 가능, version 증가)
effective = base * consumption_ratio
if ratio == 0 and <K05: 함수가 0 거부>:
    nutrition = {k: 0.0 for k in 기존 6개 키}
else:
    nutrition = calculate_nutrition(<K05로 확인한 class_id>, effective)['nutrition']
```
- 비율은 유한한 숫자 0~1. JSON 정수 0·1 허용, bool·문자열·null·NaN 거부. `expected_version`은 strict 양의 정수, request ID는 UUID.
- **현재 snapshot에 비율을 다시 곱하지 않는다.** 정정은 CSV × 기준 배율 × 새 절대 비율로 계산한다.
- 기존 6개 키·단위(cal kcal, sodium mg, 나머지 g)·소수 2자리 snapshot 정책을 유지한다. 새 키·그램 값을 만들지 않는다.
- JSON 컬럼은 **새 dict를 대입**한다(제자리 수정 금지).
- 클라이언트가 보낸 영양값·합계는 받지 않고 서버가 계산한다.
- 기존 행은 `consumption_ratio=1`, `version=1` 기본값. 기존 snapshot 불일치는 자동 보정하지 않고 보고한다.
- 영양 CSV 경로와 SHA-256을 보고서에 기록한다.

## 10. 트랜잭션·멱등성·변경 이력

잠금 순서를 정해 문서화한다(**대화/초안 → 식사 → 항목**). 모든 판정은 행 잠금 **이후**에 한다.

- **메시지:** 같은 client_message_id·같은 내용 → 기존 결과 반환. 다른 내용 → 409.
- **업로드:** upload_request_id에 checksum·메시지를 묶는다. 같은 재시도는 같은 첨부 반환, 다른 내용이면 409.
- **초안 수정:** version 비교 후 갱신. 오래된 변경은 409, 다른 탭의 최신 값 보존.
- **초안 확정:** 초안 행 잠금 → 소유권·version·상태 확인 → Meal/MealItem 생성(K17의 서비스 함수, 내부 commit 없음) → 사진·초안 항목 매핑 → `confirmed` → MutationRequest 결과·성공 메시지·이력을 **한 트랜잭션**으로 기록. 내부 HTTP 호출로 create 후 patch하는 방식은 원자성 대체가 아니다.
- **확정 식사 수정:** 항목 행 잠금 → MutationRequest 중복 확인 → version 비교 → ratio/nutrition/version 수정 → 이력·성공 메시지·결과를 같은 트랜잭션에 저장.
- **재시도 규칙(R2·R10):**
  - 같은 request_id·같은 payload → 쓰기 없이 **원래 결과**(결과 ID·version) 반환. 이미 다음 변경이 있었다면 화면은 최신 리소스를 별도 재조회한다. 다른 저장이 끼어든 뒤의 지연 재시도(A→B→A)도 A의 원 결과를 돌려주고 B 상태를 덮어쓰지 않는다.
  - 같은 request_id·다른 payload → 409 `request_id_conflict`. payload hash는 필드 순서·숫자 표현을 정규화한 명령 내용에 기반한다.
  - 새 request_id인데 `expected_version`이 다르면 → 409 `version_conflict`.
  - 같은 expected_version의 동시 수정은 하나만 성공, 나머지 409.
- 실패한 식사 쓰기는 rollback한다. 수신 완료된 사용자 메시지는 유지하고 처리 상태만 failed/retryable로 기록할 수 있다. 성공 메시지·성공 이력은 남기지 않는다. 같은 request_id로 재시도할 수 있다.
- 중복 메시지로 응답이 중복 생성되지 않게 응답/행동 연결에 제약을 둔다.

## 11. API와 프론트 계약

논리 계약이며 기존 라우트·서비스에 매핑하고 중복 경로를 만들지 않는다. 모든 조회·쓰기·사진에 인증·관계 검증을 적용한다. 404: 미존재·타 사용자·관계 불일치. 409: `version_conflict` / `request_id_conflict` / `invalid_state`. 422: 입력 검증.

| 기능 | 제안 인터페이스 | 쓰기 효과 |
|---|---|---|
| (A1) 대화 생성/복원 | POST/GET conversations, GET messages(cursor) | 생성만 쓰기 |
| (A1) 사진 업로드 | POST conversation attachments(request_id, file) | 첨부·사진 메시지 저장 |
| 사진 분석 | POST attachment analysis(동기) | 분석 결과·초안·응답 저장 |
| (A1) 메시지 전송 | POST conversation messages(client_message_id, text, target, expected_version) | 원문·응답·초안 변경·처리 상태 |
| (A1) 초안 조회 | GET drafts(새로고침 복원용, 읽기 전용) | 쓰기 없음. 초안 변경은 메시지 처리로만 |
| 식사 확정 | **별도 공개 확정 경로 없음.** 메시지 전송 처리 안에서 서버 서비스가 호출(내부: draft confirm, expected_version·request_id는 메시지의 client_message_id·초안 version에서 유도) | 원자적 식사 생성·연결 |
| (A0) 확정 식사 해석 | POST meals/consumption/interpret(text, item_id?, meal_id?) | **확정 식사 쓰기 없음**(대화 경유 시 메시지만) |
| (A0) 확정 식사 미리보기 | POST meals/items/{id}/consumption/preview(ratio) | 확정 식사 불변 |
| (A0) 확정 식사 수정 | PUT meals/items/{id}/consumption(ratio, expected_version, request_id) | 기록·이력·응답 갱신 |
| (A1) 이미지 조회 | GET attachments/{id}/content | 소유권 확인 후 제공 |
| (B) 변경 구독 | GET user events(cursor) | **B** |

요청 스키마(`RequestModel` 상속): `consumption_ratio` — 0~1, JSON 정수 0·1 허용, bool·문자열 거부(K09 결과로 구현) / `expected_version` — strict `int ge=1` / `request_id` — `UUID` / `text` — 길이 상한(예: 200자) / 첨부 용량·페이지 크기는 기존 정책을 따르고 없으면 설정으로 명시.

미리보기 응답: `item_id, meal_id, food_name, unit(CSV 단위 문구), version, before{consumption_ratio, effective_multiplier, nutrition}, after{…}`

공통:
- 실패 응답에 내부 오류·스택을 노출하지 않는다(일반 한국어 메시지, 로그에만 기록).
- **플래그 on일 때만** `meal_json`에 `consumption_ratio`, `version`, `effective_multiplier`(A0), 사진 연결(A1)을 **추가**한다. 기존 키는 유지한다. 플래그 off에서는 기존 응답과 완전히 같다(P3).
- 섭취량 수정·정정은 `apply_correction`을 호출하지 않고 `RetrainingSample`을 만들지 않는다. 새 식사 **확정** 시에만 R12 규칙을 따른다. 모든 새 라우트는 플래그 뒤에 등록한다(P3).

프론트:
- **(A0)** `MealHistory.jsx`에 "챗으로 수정" 진입점과 입력창(텍스트 입력, 해석 결과, 전·후 6개 값, 성공·실패·확인 질문·값 불일치 상태). 비율 버튼·저장 버튼 없음(R14). 기존 `api()` 헬퍼와 CSRF 재사용(K14).
- **(A1) 화면 구성은 5.0장 명세를 따른다.** 새 컴포넌트(예: `ChatRecord`, `FoodCardReadOnly`, `SavedMealCard`, `TodayMiniSummary`, `RecentMealsMini`)는 모두 신규 파일로 만든다. 비율 버튼·조정 패널·저장 버튼 컴포넌트는 **만들지 않는다.** 메시지 응답에 초안·확정 결과 snapshot(항목·합계 영양)을 포함해 화면이 계산하지 않게 한다.
- 새로고침 후 서버의 진행 중 초안과 선택 대상을 복원한다. 진행 중 초안을 임의로 새로 만들지 않는다.
- 저장 후 과거 확인 카드가 최신 값으로 바뀌어 대화 증거를 잃지 않도록 **당시 카드 snapshot과 최신 식사 카드를 구분**한다.
- `MealHistory.jsx`의 "챗으로 수정" 버튼은 연결된 대화로 이동하거나 식사 연결 대화를 만든다.
- 메시지의 `client_message_id`는 전송마다 새로 만들고 같은 메시지의 재시도에는 같은 값을 쓴다(자동 저장의 멱등 키). `crypto.randomUUID()`가 없으면(비보안 컨텍스트·LAN IP) `crypto.getRandomValues` 기반 UUID v4로 대체한다. 전송 중에는 전송 버튼을 비활성화해 같은 문장의 중복 전송을 막는다.
- 저장 성공 후 히스토리·오늘 상태를 재조회한다. 월간이 React이고 열려 있으면 함께 재조회한다(K12). 실패 시 성공 메시지를 보이지 않고, 409면 안내 후 최신 내용을 불러온다.
- 기존 화면의 `serving_multiplier` 표시는 수정하지 않는다(R9). 유효 배율은 새 화면에서만 표시하고, `meal_json`에 추가한 `effective_multiplier`는 후속 반영용으로 제공만 한다.
- 모든 새 진입점·화면은 `CHAT_RECORD_ENABLED`가 켜졌을 때만 나타난다(P3).
- 업로드·분석·대화 처리·초안 저장·식사 확정의 상태를 구분해 표시한다. API helper와 CSRF를 재사용한다.
- 프론트 자동 테스트 체계는 없다. `npm.cmd run build` + 수동 시연으로 확인한다.

## 12. 반영 시점과 실시간

**A0·A1**
- 저장 API 성공 응답 직후 현재 화면을 서버가 확정한 내용으로 갱신한다. 낙관적 표시에는 "전송 중" 상태를 둔다.
- 접속·재로그인·포커스 복귀 시 최신 대화·초안·식사를 재조회한다. 짧은 주기 재조회는 보조 수단이며 **실시간 푸시 완료로 보고하지 않는다.**
- 과거 날짜 식사 수정은 오늘만이 아니라 해당 날짜·월 데이터를 갱신 대상으로 삼는다.

**B**
- 기존 푸시가 없으므로 세션 인증을 쓰는 사용자별 **SSE + DB ChangeEvent(outbox)**를 기본안으로 한다.
- 변경 커밋과 이벤트 저장은 원자적이다. 커밋되지 않은 데이터를 성공 이벤트로 보내지 않는다.
- 이벤트는 대상 ID·종류·version·event_id만 보내고, 화면이 인증된 API로 최신 내용을 조회한다. 중복 전달은 event_id로 걸러내고, 재연결 시 cursor부터 이어 받으며 유실·보존기간 초과 시 전체 재조회한다.
- 서버 프로세스가 여러 개여도 DB outbox를 읽어 변경을 놓치지 않는다. SSE 구독도 소유권을 검증하고 세션 만료 시 종료·재로그인을 안내한다. CSRF는 상태 변경 API에 기존 규칙대로 적용한다.
- 정상 로컬 환경에서 커밋 후 다른 탭 반영까지 **2초 이내를 목표 수용 기준**으로 측정하고 측정 환경·시간을 보고한다(무조건적 성능 보장이 아님). 분석 소요시간과 반영 지연을 구분해 측정한다.
- 실제 네트워크 단절 중에는 최신 상태를 보장하지 않는다. 재연결 후 누락 없이 맞춰지는지를 검증한다.

## 13. correction과 migration

- **correction (R3):** 기존 경로는 **수정하지 않는다.** 이 경로는 `serving_multiplier`만 곱해 `nutrition`을 다시 쓰므로 섭취량을 수정한 항목의 음식을 바꾸면 영양값이 비율 1.0 기준으로 돌아간다. 관찰해 팀 협의 자료로 보고하고 "correction 연계 미완료"로 표기한다(실패가 아니라 예상된 결과). 보완 패치(`serving_multiplier × consumption_ratio`로 재계산 + `version` 증가, `ratio=1.0` 행에서 기존 동작과 동일)는 **별도 커밋으로 준비만** 하고 사용자 승인 후에만 적용한다.
- **어긋남 감지(A0):** "챗으로 수정" 진입 시 저장된 `nutrition`이 CSV × 기준 배율 × 비율과 다르면 원인을 단정하지 않고 "저장된 값이 현재 계산과 달라요. 저장하면 현재 기준으로 다시 계산돼요."를 표시한다. 확정 발화로 저장하면 CSV에서 다시 계산한다. 원인은 correction·기존 데이터 불일치·CSV 변경 어느 것이든 될 수 있다. 진입만으로는 쓰기·자동 보정을 하지 않는다. UI에서 숨기는 것만으로 API 충돌이 해결됐다고 보고하지 않는다.
- 저장 전 초안의 음식 정정은 식사·탐지 원본을 바꾸지 않는다. 최종 음식과 기준량 확인 후 확정한다.
- **migration (R16):** 실제 head(K08) 다음에 **개인 브랜치에만** 작성한다. **A0와 A1은 별도 revision**(예: `20261013_01_consumption.py`, `2026xxxx_01_chat_record.py`). 상단에 "TEST-ONLY: 개인 브랜치 한정, 팀 반영 시 Backend Core A 담당 이관"을 적는다. 제약·FK·unique·NOT NULL·기본값을 모델과 migration에 함께 반영하되 **additive만 허용**한다(P4). `last_request_id` 컬럼은 만들지 않는다.
- 수정 전 테스트 데이터로 upgrade→downgrade→upgrade 왕복과 기존 데이터 보존을 확인한다.
- 수정 **후**의 복구는 **DB와 사진 파일의 사전 백업 복원**으로 검증한다. downgrade만으로 원복됐다고 보지 않는다.
- 운영 데이터 자동 보정·초기화는 하지 않는다.

## 14. 검증 사례

자동 테스트는 새 파일(`backend/tests/test_consumption.py`, `backend/tests/test_chat_record.py` 등)에 작성한다. `test_p0_flow.py`의 `env`·계정 생성 패턴을 복제하고 **기존 테스트 파일은 수정하지 않는다.** 새 테스트는 플래그 on 상태로 실행한다. 모든 사례에 **통과 / 실패 / 미실행 / 관찰**과 근거를 기록한다. 사진 관련은 mock과 실제 촬영 시연을 구분한다.

**기대값 규칙**
- 기준 데이터: CSV class_id 2 `갈비구이`(`인분 (약 200g)`, cal 723.0 / carbs 4.8 / protein 77.7 / fat 43.7 / sugar 0.8 / sodium 1206.0), 배율 1.0, 직접 선택 저장 항목. K10에서 값이 다르면 실제 값으로 바꿔 보고한다.
- cal·sodium은 **고정 숫자로 독립 단언**한다(예: 361.5, 603.0). 반올림 영향 키(예: fat 43.7×0.25=10.925)는 `calculate_nutrition(class_id, base×ratio)` 결과와 비교한다.
- CSV 해시는 보고서에 기록만 하고 테스트에서 단언하지 않는다.
- "불변"은 **확정 식사·집계 불변**을 뜻한다. A1에서는 대화·메시지·초안 기록이 생길 수 있다.

## 17. 제출물

각 판정 보고(착수·A0·A1) 때 해당 범위만 제출한다.

1. 기준/작업 커밋과 변경 파일 목록, **기준 커밋 대비 `git diff --stat`과 P2 목록 대비 판정**(T52), 플래그 off 회귀 결과(T47). correction 보완 패치를 준비했다면 그 커밋 식별(미적용).
2. 착수 확인표 K01~K20(결과·근거·판정), S0 결과와 시연 구성, CSV 경로·SHA-256, 기준 응답 스냅샷 파일 위치.
3. 실제 모델·API 매핑, 요청/응답 예시, (A1) 상태 전이 설명.
4. 신규 migration(A0·A1 각각), 기존 데이터 영향, **DB·사진 백업 복원 방법**.
5. 실행 방법(백엔드·프론트·테스트 명령, S0 설정 명령), 환경변수 이름·목적·기본값. 실제 비밀값 미포함.
6. 해당 범위 테스트의 **통과 / 실패 / 미실행 / 관찰** 표와 로그·**화면 캡처(웹·모바일)**.
7. 구분 표시

   | 항목 | 값 |
   |---|---|
   | 대화 해석 | 규칙 기반(LLM 미사용·미검증) |

   | DB | SQLite / PostgreSQL 각각 실행 여부 |
   | 동기화 | 현재 화면 / 같은 PC 다른 탭 / 실제 다른 기기 |

8. 완료 상태를 **각각 따로** 표기: A0 / A1(사진·대화 영속성, 자동 확정, 정정, 재접속 복원) / correction 연계(예상: 미완료) / PostgreSQL 동시성 / 실제 사진·휴대폰 촬영 / B. 하나라도 미실행·미완료면 "전체 통합 완료"로 보고하지 않는다.
